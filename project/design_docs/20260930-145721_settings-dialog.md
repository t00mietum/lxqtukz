## Summary

Settings is one app for every desktop and system setting a person is likely to change, along the lines of KDE's System Settings. Over time it replaces the separate settings tools, starting with LXQt's configuration center and its modules. Its tabs are listed down the left side. It works fully from the keyboard, and changes show live on the desktop where the component allows it.

The app is designed declaratively, the same as SilkTerm's settings dialog. Its tabs, groups, rows and layout are declared in a `.shcl` configuration file, and the code only reads, writes and formats values.

The layout and behavior rules come from SilkTerm's settings dialog design. See [Credits](#credits).

## Specification

- Settings is its own app window. It is launched from the menu, the panel or the command line.

- Every tab, group and row, and the layout's measurements, are declared in a `.shcl` file compiled into the app. Adding a setting means a new row in that file, plus the code that reads and writes its value.

- The tabs run down the left side. The first are Screensaver and power, Keyboard and Mouse, in that order of priority. Desktop, for wallpaper and icons, comes from tukzdesk. Settings about one subject sit on one tab, even when different components keep them.

- A tab may have tabs under it instead of rows. Every tab is listed, and the sub-tabs are stepped in under their parent. A parent with a sub-tab open reads as current along with it.

- Each tab has groups, which are titled sections. Inside a group, a switch and the rows that depend on it form a sub-group, with the dependent labels stepped to the right. Rows that only count while their switch is on stay live while it is off.

- A row that cannot act right now is grayed out, and its flyover says why. A grayed row takes no click.

- A setting the system can work out for itself is automatic until a value is set.

- Every row whose value is not its default shows a revert arrow. A click on it puts the default back.

- A fraction is shown as a whole percent. A unit is shown in the label, such as px, ms or s.

- The footer has Cancel, Apply and OK.
	- Apply saves and applies, and the window stays open.
	- OK does the same and closes.
	- Cancel closes without saving, and the live preview is undone.
	- Enter is OK and Esc is Cancel, even inside a text field. While Alt is held, the buttons underline a letter, and Alt with that letter presses the button.

- Each file gets only what was edited. Settings reads the files again each time it opens, so it shows changes saved elsewhere.

- If a settings file has a line that cannot be read, a save to it is refused, and an error box says so and names the line. OK still closes. If another program seems to have the file open, the change applies for the session, nothing is written, and OK leaves the window open.

- The whole app can be driven from the keyboard.
	- Tab and Shift+Tab walk every control, then the footer buttons, and wrap. Headers and grayed rows are skipped.
	- Ctrl+Tab, Ctrl+Shift+Tab, Ctrl+PgUp and Ctrl+PgDn change tabs. A tab with sub-tabs is walked through them, and the step after its last one goes on to the next tab.
	- Tabs take no focus. They are clicked, or changed with those chords, and otherwise only say where you are.
	- A text box takes Ctrl+C, X, V and A, and Ctrl moves by words.
	- Space toggles, and the arrow keys adjust.
	- Walking onto a text, number or color field selects its value.

- Text fields behave like text fields everywhere else: mouse and keyboard selection, word moves, the clipboard, and a right-click menu with Cut, Copy, Paste, Delete and Select all.

- A color chip opens a color picker. Edits in the picker show at once, and Cancel puts the old color back.

- The window opens at the size its content needs, capped to the screen's work area. It can be resized, and the rows scroll when they do not fit. The size is kept for the rest of the session.

- Reopened within a minute, the app comes back on the same tab and scroll position. Values are never kept from the last time.

- The window follows a change of display scale without losing unapplied edits.

- Opening Settings takes well under a tenth of a second.

## Goals

- Every desktop and system setting a person is likely to want is in this app, and reachable without editing a file.

- A person can find a setting by what it changes on screen, not by which component keeps it.

- Nothing in the app lies. A grayed row says why, a percent is a percent, and a row that looks editable saves when edited.

- The app looks and behaves the same at any display scale.

### Non-goals

- Every setting in every file. Some stay file-only.

- X11. LXQtukz runs only on Wayfire.

## Design

### Toolkit

- Rust, with a Qt Quick interface through cxx-qt. The settings code is Rust, as in SilkTerm, and reads the declarations with shcl's Rust crate.

- The controls come from KDE's desktop style for Qt Quick, which draws them through the Qt widget style. So the app follows the same theme as every other Qt app, Kvantum and each personality included. Fusion stands in where that style is not installed. That style takes its colors from a KDE color scheme rather than the palette, so the app writes one from the palette at startup.

- The interface is generic QML. It lays out whatever the declarations list, and knows no setting by name.

- Qt already scales by display, moves focus with Tab, and edits text with selection, word moves and the clipboard. So those parts of this design come with the toolkit, and the layout rules are the parts left to write.

### Where settings are written

- Settings writes the files of the [configuration model](../design.md#configuration-model): each LXQt module's `.conf` and `wayfire.ini` under `~/.config/lxqtukz/`. It never writes a component's own path outside that model.
	- Wayfire's file is the exception. Settings writes the file the running Wayfire was started with, named in `WAYFIRE_CONFIG_FILE`, so it works in whichever Wayfire session it runs from. In an LXQtukz session that is `~/.config/lxqtukz/wayfire.ini` anyway, and that is also where it goes when the variable is unset.

- tukzdesk's settings go through tukzdesk's API. tukzdesk's own settings app is removed once the Desktop tab covers it.

- A write keeps comments and every line nobody changed.

### Declarations in shcl

The interface lives in a `.shcl` declarations file, compiled in, as SilkTerm's settings dialog does with `settings_ui.shcl`. It says which rows exist, their order, the heading and tab each sits under, the setting behind each row, the graying rules, and all of the layout's measurements. The code keeps only behavior: how a value is read, written and formatted.

- A row's name is the setting it edits. A heading starts a group and names its tab, by path where the tab sits under another.

- A test fails if a row names a setting the code does not know, or leaves one out. It is the only thing that catches a row that is missing altogether.

- Another test drives every row through a save and a relaunch. A row whose setting is never written would otherwise change the session and be gone at the next login, with nothing to say so.

- A heading whose label is its own tab's title takes no space and draws nothing, since the tab list has said it already. It still has to be declared, because a heading is what assigns the rows under it to a tab.

### Tabs down the side

- `tabs:` lists paths, `Keyboard/Shortcuts` being Shortcuts under Keyboard. A tab with tabs under it has no rows of its own, so there is always one sub-tab on show while it is current. A click on it opens its first, unless the current tab is already under it. A heading names its tab by that path. Any depth is allowed, though past 2 levels it is poor design rather than a limit of the code.

- The tab list is the panel's height, with every tab in it, each entry as wide as the list and a sub-tab stepped in by `tab_indent` per level. A list taller than the panel slides only far enough to keep the current tab in view.

- The current tab and every tab it sits under draw as current. A sub-tab says which parent it belongs to that way, and a parent says that something under it is open.

- The tab chords walk the leaves in list order. That one rule runs through a tab's sub-tabs and on to the next tab after the last of them.

- Tabs are never focus stops, and a click on one leaves nothing focused. They are chrome that says where you are.

### Groups, sub-groups and units

- A group is a titled section with a rule under it and clear space above.

- A sub-group has no title of its own. It is a control followed by the controls that depend on it, whose labels step right so the run reads as belonging to the leader. A master switch and the things it governs is what this exists for, such as the screensaver switch and its timeout.

- Only labels move. Every control keeps the one column it shares with every other row, because a settings list is scanned down that column, and a control that wandered with its label would break it.

- A sub-group is read off the indentation in the declarations rather than declared a second time, so the leader and its members cannot disagree about who belongs to what.

- A fraction stored as a decimal is shown as a whole percent. Nobody thinks in 0.35, and the file is a different audience from the app. The conversion is exact both ways, so reverting a row gives back its own default rather than a hair off it.

- The unit is part of the label, and the help line does not repeat it.

- A `beside` row shares the line above it, splitting the control column in half. One revert arrow on the first half answers for both.
	- Several `beside` rows in a row make a line of that many parts, split evenly.
	- A line of nothing but toggles packs at its own width instead. Each label sits right before its own box, and a wider gap comes before the next label. The gaps grow with the interface line height above the default font's, and never shrink below it.
	- A packed line that shares its group with other rows keeps its first label and box in their columns, so that box lines up with the boxes above it. Only the toggles after it pack. This is read off the group, not declared, the same as a sub-group.

- A checkbox and a radio box grow with the interface line height at one rate, so at a large font they come out one size. Each keeps its declared size as a floor.

- A slider's number field is measured the way the labels are. Its width is the longest number any slider can show in the interface font, plus the field's padding. One width serves every slider, so they all end in one column. It never drops below the floor in the declarations.

- The other columns of text are measured the same way, each with its declared width as the floor. A measured width is rounded down to a whole DIP. A column of user-entered names cannot be measured ahead, so it grows with the interface line height instead.

### Sizes and display scaling

- Every measurement in the interface is written once, in device-independent pixels (DIP), and turned into real ones only when it is drawn. A DIP is 1/96 of an inch, so a border, a gap or a checkbox is the same physical size on any screen.

- The layout is solved end to end in DIP and converts once, where it meets its window. A stray conversion inside would scale something twice.

- A measurement taken in real pixels converts the constant beside it into real pixels, rather than being converted itself. Text is measured against the font, which is real pixels by nature, and the clear space around it is written in DIP. Adding the two as they stand and dividing the sum at the window's boundary shrinks the constant by the scale factor. Every such site converts the constant where it is used, through one rule.

- Conversion rounds to whole pixels. A rule or a hairline that fell between pixels would come out soft. A measurement asked to be visible never rounds away.

- A raw-pixel mistake is invisible at 1x and only shows as the scale rises. An environment override for the scale factor lets a high-DPI layout be checked on an ordinary display.

- An open window follows a scale change in place rather than being rebuilt. Moving it to a monitor at another scale, or changing the scale under it, moves only the boundary. A rebuild would lose every unapplied edit. The size kept for the session is in DIP for the same reason.

- With a toolkit that scales on its own, such as Qt, these rules become checks on its output rather than code of our own.

### Window size and scrolling

- The window's natural height is its tallest tab's, leaving out tabs that grow with a list. Those scroll rather than making every tab as tall as their list.

- The window opens at its natural size, capped by the work area of the monitor it opens on: the monitor less the panel and docks. Wayfire places it.

- The window can be resized. Rows scroll vertically only when they overflow, and a horizontal scroll bar above the footer appears when the window is narrower than its content. The tab list and the footer buttons never scroll. The size snaps to natural when dragged near it, and is kept for the session only.

- The widest label on any tab sets the panel's width for every tab. The tab list adds its own width on top, set by its widest entry at its step in.

- There are 2 coordinate origins, window and content, and a control must be drawn and hit-tested in the same one.

### Chrome

- The app follows the current personality's theme. Its accents use the theme's 2 attention colors, the accent and the focus color. The pressed-button fill is the accent mixed back toward the panel, which is what makes a pressed button read as pressed rather than focused. Only OK has the accent outline.

- A focused field shows a single outline. The ring sits exactly on the box's own outline, and the box stands its border down. Where the focused thing is not a box, such as a checkbox or a slider handle, the ring sits a little outside it. A color row's ring spans the chip and the hex field.
	- A ring that takes in the labels after its boxes, as a radio group's does, is never shorter than the labels' line.

- The tabs sit on a recessed gutter, with a rule along its right. The current tab is a lighter gray rather than an accent, since "you are here" is a different job from "look at this".

- Controls whose label does not explain them have a line of flyover help, 1 to 3 sentences. One that is grayed out explains why instead, that being the more urgent question at the time. A tip is kept only if it says more than the label. The text wraps to the panel. Tips wait for the pointer to rest. A row's tip shows over all of it, label, options and controls alike, and only the revert arrow answers with its own. None shows while a dropdown list or the field menu is open, or while the window does not have the focus.

- The app draws in the desktop's interface font. Everything sizes off that font, so a larger interface font makes the panel wider rather than clipping it.

- Text centers on its glyphs rather than its line box. Each control centers in its actual row.

### Controls

- Text fields keep a horizontal offset that scrolls ahead of the caret and scroll on drag. A fresh click selects all on release, while a drag keeps its range. A paste is checked by the field's own validation.

- A slider is 2 focus stops, the track and then its number field. Up and Down step about a hundredth of the range, Shift about a tenth, and Left and Right do the same. Pixel sliders step in whole units. A number typed into the field is clamped. A row with no % and no limit of its own lets it go past the slider's end, up to a cap. A slider over a wide range of times, such as a screensaver timeout, can use a log track.

- A dropdown opens on a click, Space or Alt+Down. Up and Down move the selection, Enter or Space picks, Esc closes, and Left and Right step without opening. Its list draws on top, and it opens upward when it would spill past the panel.

- Buttons center their captions, fire on release, and cancel if the pointer is dragged off first.

- The revert arrow is mouse-only. It is accent-colored and clickable when a value is off its default, and dim at the default. On Apply, a reverted key is dropped from the file and the default line comes back.

- A row whose effect only shows after a wait, such as screen off or the screensaver, has a "Test now" icon left of its revert arrow. It is declared with `test:`, with its own flyover from `test_help:`. The test starts once the keyboard and mouse rest for a second, and ends at the next key or mouse move. Like the revert arrow, it is mouse-only.

- Key repeat has a test area under it, a field to hold a key down in. It stores nothing. Enter in it is a key to try, not OK.

- A row that depends on something outside Settings, such as screen power on a monitor that may ignore it, has a warning mark after its label, declared with `warning:`. That text goes on the end of the row's flyover.

- A row under a switch shows the switch's answer while the switch is on. Typing in it turns the switch off. Turning the switch on again sets the typed value aside, and off brings it back. Nothing is grayed for any of this. The relations are declared on the rows, with `gate:`, `auto:`, `rule:` and `group:`.

- The app has one open edit at a time, and other fields that need text editing borrow it, such as the color picker's value boxes. That is how all of them get selection, word moves and the clipboard with no second copy of the code.

### The color picker

- A color chip opens a picker: a saturation and brightness square, a hue strip beside it, 6 value boxes, and Cancel and OK. It is a modal box titled with the row's label. The hex field on the row stays where it is. Typing a known hex is faster than hunting for it, and a picker is for when the value is not known yet.

- The picker keeps the color as hue, saturation and brightness rather than as 3 bytes. Dragging to the bottom of the square leaves black, which says nothing about hue, and dragging to the left edge leaves a gray, which says nothing about saturation. Reading the model back off the bytes each frame would send both markers home the moment the color reached an edge. The bytes are derived from the model, and the trip back is exact for every color.

- Changes go straight to the row behind the box, and Cancel puts back what the row had when it opened. That makes the chip, and the desktop behind the window, the preview. There is no second copy of the value to get out of step.

- The value boxes are red, green and blue as whole percents, then brightness, saturation and a hex value. There is no hue box. The strip is the hue control, and the other 5 can already name any color between them. Percents rather than 0 to 255, because every other fraction in the app shows as a whole percent.

- The chip is a focus stop of its own, so a color row has 2: the chip, then the hex field. Walking onto the chip opens nothing, and Space or Enter opens the picker. Without that the picker would be the one thing in the app a keyboard could not reach.

- Inside the box, the arrows adjust whatever has focus: the square by a hundredth of its range, the strip by a hundredth of a turn, and a value box by a hundredth of its own range. That is the same step every number box in the app takes.

### Apply, OK and Cancel

- Every change applies live where the component can take it, so the desktop is the preview. Cancel puts the live settings back. A setting that needs a new login says so in its flyover.
	- Wayfire reads its file again whenever it changes. So for Wayfire's settings the write is the preview, and Cancel writes back the values the file had.

- Apply and OK apply the edited settings, then write the files. Each file gets only what was edited.

- The baseline is reset after each Apply, so a second Apply of another change works.

- Apply puts the default line back only for rows still at their default.

- Settings reads the files again each time it opens, so it never writes back a value another program changed and Settings did not touch.

- If a line in a file cannot be read, every save to that file is refused, since a save would drop that line. An error box says so and names the line. It is shown every time for OK or Apply, and once a session for saves nobody asked for, such as the window size. OK still closes, so the button does not seem to do nothing.

- If another program seems to have the file open, the change applies for the session and is not written, and OK leaves the window open to try again.

### Reopening

Closing and reopening Settings within a minute comes back on the same tab and scroll position, for any kind of close. Values are never kept from the last time. The position is clamped to the new window.

## Open questions

- System-wide settings, such as the admin's files in `/etc/xdg/lxqtukz/`. They need root, through polkit or a separate admin mode.

- How tukzdesk's API describes its settings, and whether its rows are declared here or by tukzdesk.

- Which idle, lock and display power programs the Screensaver and power tab drives on Wayfire.

- Which LXQt configuration tools are replaced first, and when each leaves the build.

## Alternative ideas

### Unconsidered

- A visible alert around a setting that changed because of another one.

- A search box across every tab, as in KDE's System Settings.

### Rejected

- SilkTerm's own self-drawn dialog, moved into a shared crate. It is the closest to this design, but the app would have to bring its own accessibility, input methods and text editing.

- Qt Widgets in C++. The closest fit to LXQt, but not Rust.

- Slint with its Qt style. Rust, but drawn in software only, and not licensed LGPL.

- Rebuilding the window on a scale change. Simple, but it loses unapplied edits.

- Separate theme colors for tips. Tips take shades derived from the chrome instead, the way menu hover and borders do.

- A hue value box in the color picker. The strip is the hue control.

- A preview chip in the color picker. The row's own chip, and the desktop behind it, are the preview.

### Superseded

- Tabs across the top. The baseline supported both places, with `tabs_side: top` or `left`. LXQtukz uses the left only.

- A separate settings app per component, such as LXQt's configuration center modules and tukzdesk's own settings app. They are replaced by this one.

## Roadmap

- The first tabs, in order of priority:
	- Screensaver and power: a screensaver manager and screen power management.
	- Keyboard: delay, speed and shortcuts.
	- Mouse.

- The Desktop tab, through tukzdesk's API. Then tukzdesk's own settings app is removed.

- The rest of LXQt's configuration modules, each removed once its tab covers it.
